# Monomi Digest Topic Pages Specification

- **Version:** 0.1
- **Status:** Implementation approved / visual acceptance pending
- **Backlog ID:** BL-051
- **Approved scope:** topic-page v0.1, documentation, dedicated branch, commit, and PR
- **Approval evidence:** 2026-09-01 user message: 「書同期とテーマページv0.1、branch作成・commit・PRまで進めてOK」

## 1. Purpose

Monomi Digest currently has a daily top page and date-oriented Archive. Topic pages add a second navigation axis so accumulated articles can be found by subject across dates. v0.1 reuses classifications already present in the validated daily digests instead of creating a new taxonomy pipeline.

The purpose is information architecture and reuse of accumulated articles. Search discovery is a secondary benefit; v0.1 does not assume that topic pages themselves improve ranking.

## 2. Classification contract

1. Existing ARTICLE `category` is the primary classification signal.
2. Existing ARTICLE `tags` are cross-cutting signals; a topic may include an article whose primary category differs when a registered tag matches.
3. No new Gemini request, prompt, response schema, daily JSON field, or historical data rewrite is introduced.
4. `Entity` extraction is not part of v0.1 and remains a future option.
5. `その他` is not a public topic.
6. Topics are curated in an explicit registry; every tag does not automatically become a page.

## 4. Publication gate

A registered topic is public only when both conditions hold:

- at least **5 matching articles**; and
- matches across at least **2 distinct digest dates**.

The topic index is always generated. A registered topic below the gate is omitted from the index and detail output. If a previously generated registered topic later falls below the gate, only that registry-owned directory is removed; unknown siblings under `docs/topics/` are not swept.

## 5. URL and navigation contract

- Topic index: `/topics/`
- Topic detail: `/topics/{slug}/`
- Top page adds one global navigation link: `テーマから探す` → `topics/`.
- Existing digest navigation remains unchanged.
- Topic article titles link to the exact daily Archive card: `/archive/{YYYY-MM-DD}.html#article-N`.
- `N` is computed from the same `fetch.sort_items_for_display()` order as the daily Archive.
- Existing article-card tag pills remain non-clickable.

## 6. Topic page content and source-policy contract

### Topic index

Each public topic shows its label, article count, number of distinct digest dates, latest matching date, and a deterministic description.

### Topic detail

Each matching entry may show:

- original article title where available;
- digest date and source;
- importance and confirmation timing when available;
- existing ARTICLE summary when available;
- source-policy-required attribution generated by the existing `fetch.render_source_attribution_html()`; and
- a safe HTTP(S) `元記事を読む` link when an original URL is available.

The entry title itself links to the canonical daily Archive card. The full `financial_impact`, `recommended_actions`, NVD/KEV facts, and full article card are not duplicated; the daily Archive remains the canonical detailed reading surface.

**BL-032 preservation is mandatory.** A topic page is a new public surface, not an exception to `SOURCE_USAGE_POLICY.md`. When stored AI analysis is displayed, the topic generator must preserve the same mode-specific attribution requirement already used by the daily article card. For `limited_feed_analysis`, the original title is preferred and the generated Japanese title must not be reintroduced. Original article URLs pass through the existing HTTP(S)-only `fetch.safe_url()` contract. No topic-page code may recover or publish purged publisher excerpts.

## 7. Search metadata and crawl discovery

- Every topic page has a deterministic unique `<title>` and meta description.
- Every topic page has one absolute HTTPS apex canonical URL.
- v0.1 **does not modify `docs/sitemap.xml`**. The accepted BL-009 Phase A-3 sitemap generator/URL-set contract remains unchanged.
- Topic pages are crawl-discoverable from the public top page through `テーマから探す`.
- Adding `/topics/` to the sitemap is a separate follow-up only if the project explicitly supersedes the Phase A-3 crawl-file contract.
- The existing Cloudflare Web Analytics footer/beacon renderers are reused; no new analytics provider or third-party script is introduced.

## 8. Generation architecture

`fetch.py` remains the primary daily collector/generator. `topic_pages.py` is a deterministic post-generator that runs after `python3 fetch.py` and before the existing production commit step.

It:

1. reads only validated published digest dates;
2. derives matches from existing display items;
3. preserves Archive visible order for article anchors;
4. preserves source-policy attribution and safe original links;
5. writes `docs/topics/...`;
6. injects one top-page topic link with an idempotent fail-closed marker; and
7. leaves the Phase A-3 sitemap byte-for-byte untouched.

No network request, Gemini call, source collection change, or daily JSON mutation is required.

## 9. Scope boundaries

Allowed changes are `topic_pages.py`, its tests/specification, workflow ordering needed to generate/test the pages, project-state documentation, and a narrowly scoped correction of a pre-existing analytics test whose provider-copy assertion accidentally scanned article body/title content.

Out of scope: ARTICLE/BRIEF prompts, daily JSON schema or stored `data/*.json`, source definitions/policy semantics, relevance/promotion rules, Gemini/NVD/KEV behavior, existing daily article-card interaction, sitemap ownership in v0.1, Entity extraction, automatic pages for every tag, production dispatch, Pages/DNS/repository settings.

## 10. Verification and acceptance

Implementation verification requires tests for registry/gate behavior, Archive-anchor alignment, HTML escaping, safe original URLs, source-policy attribution preservation, original-title preference, metadata/canonical values, analytics reuse, top-navigation idempotence/fail-closed behavior, sitemap non-modification, stale registered-topic cleanup, workflow ordering, and the full existing unittest suite after realistic topic generation against the committed corpus.

Branch/commit/PR creation is authorized. Merge, production execution, and final visual acceptance remain separate actions. Final visual acceptance should cover at least `/topics/` and representative topic detail pages at PC 1280px and 390px.
